## 1. 六条锁定语义的总则

1. **权威在服务端**：SQLite 是唯一事实来源；客户端内存 store 是视图，IndexedDB 只存"最后一次成功同步的快照"用于断网兜底。
2. **存规则，不存实例**：重复日程在库里只有一条记录（含 `repeat`、`exdates`、`overrides`），显示时才展开。
3. **时间一律本地墙钟字符串**（`2026-10-08T09:30`、`YYYY-MM-DD`、`HH:mm`），**不存 UTC、不存时区偏移**。家庭日历的语义就是"家里墙上的钟指点"；全家都在同一个时区，存 UTC 只会制造换算 bug。
4. **整数 `version` 做乐观并发**，软删除（墓碑）而非物理删除。
5. **ID 一律 UUID v4**；日期字符串只做排序与索引，不做外键。
6. **一条记录三种形态**（`kind`）：`event` 进日历、`todo` 永不进日历、`countdown` 永不进日历但按年滚动。三者共用同一张表与同一套编辑抽屉，只在**读取与展开**时分道——这是为了不让"待办"变成第二套数据系统。展开引擎对 `kind !== 'event'` 的记录**硬跳过**（§5 第 0 行），否则一条未打勾的待办会在月视图里赖一整天。

## 2. 服务端 SQLite Schema

```sql
-- PRAGMA 不写进迁移 SQL：D1 由平台管理 journal/WAL，本地 node:sqlite 需要的那两行
-- 放在 server/src/db.js 的 localStore() 里，保证同一份迁移 SQL 两边行为一致。

CREATE TABLE meta (
  k TEXT PRIMARY KEY,               -- 'revision' / 'schemaVersion' / 'pinHash' / 'alarmHost'
  v TEXT NOT NULL
);

CREATE TABLE members (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  color_key  TEXT NOT NULL,          -- 枚举，见 §6
  initial    TEXT NOT NULL,
  kind       TEXT NOT NULL DEFAULT 'person',   -- person | family
  sort_order INTEGER NOT NULL DEFAULT 0,
  archived   INTEGER NOT NULL DEFAULT 0,
  revision   INTEGER NOT NULL DEFAULT 0,   -- 全局递增，增量同步靠它
  version    INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE events (
  id          TEXT PRIMARY KEY,
  kind        TEXT NOT NULL DEFAULT 'event',     -- event | todo | countdown（§3.3）
  series_id   TEXT NOT NULL,               -- = id 表示非重复系列
  title       TEXT NOT NULL,
  note        TEXT NOT NULL DEFAULT '',
  member_id   TEXT NOT NULL REFERENCES members(id),
  date        TEXT NOT NULL,               -- YYYY-MM-DD 起始日（索引主键）
  time        TEXT,                        -- NULL = 全天
  end_date    TEXT,                        -- 跨天
  end_time    TEXT,
  all_day     INTEGER NOT NULL DEFAULT 0,
  repeat      TEXT,                        -- JSON，NULL = 单次
  exdates     TEXT NOT NULL DEFAULT '[]',  -- JSON 数组：YYYY-MM-DD
  overrides   TEXT NOT NULL DEFAULT '{}',  -- JSON 对象：{ "YYYY-MM-DD": {...} }
  reminders   TEXT NOT NULL DEFAULT '[]',  -- JSON 数组：提前分钟数
  done_at     TEXT,                        -- 仅 todo：NULL = 未完成、持续显示
  sort_order  INTEGER NOT NULL DEFAULT 0,  -- 仅 todo：手动排序
  pin         INTEGER NOT NULL DEFAULT 0,
  revision    INTEGER NOT NULL DEFAULT 0,  -- 全局递增，增量同步靠它
  version     INTEGER NOT NULL DEFAULT 1,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,               -- 服务端写入时刻（ISO with tz）
  updated_by  TEXT,                        -- 设备指纹，仅用于冲突提示文案
  deleted_at  TEXT                         -- 墓碑
);
CREATE INDEX idx_events_date    ON events(date);
CREATE INDEX idx_events_member  ON events(member_id);
CREATE INDEX idx_events_series  ON events(series_id);
CREATE INDEX idx_events_kind    ON events(kind, done_at);   -- 待办与倒数日列表的主查询路径
CREATE INDEX idx_events_updated ON events(version);
```

设计取舍：JSON 列（`repeat`/`exdates`/`overrides`/`reminders`）**不建关系表**。家庭数据量下没有查询需求用到它们，展开一律在内存里做；拆表只会让"编辑一次重复日程"变成多行事务，收益为零。

`revision` 是全局单调递增整数，每次成功写入 +1，用于增量拉取与 SSE 帧去重；行内 `version` 是该行的并发计数，两者用途不同，不要混。

## 3. 客户端实体形状（camelCase，与服务端 snake_case 由 `api.js` 单点互转）

### 3.1 `Member`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | uuid | PK |
| `name` | string | 1–8 字，必填 |
| `colorKey` | enum | 固定 8 色之一，**不允许自定义十六进制**（保证色盲可辨与对比度） |
| `initial` | string | 1–2 字，缺省取 `name` 首字 |
| `kind` | `person`\|`family` | `family` = "全家"公共日历，默认存在且不可删 |
| `sortOrder` | int | |
| `archived` | bool | 归档而非删除：历史日程仍要能显示归属 |
| `version` | int | 乐观并发 |

### 3.2 `Event`

| 字段 | 类型 | 约束 / 说明 |
|---|---|---|
| `id` | uuid | PK |
| `kind` | `event`\|`todo`\|`countdown` | 默认 `event`。见 §3.3 三种形态的差异 |
| `seriesId` | uuid | = `id`（非重复）；三选一编辑的定位键 |
| `title` | string | 1–40 字必填 |
| `note` | string | ≤ 500 字 |
| `memberId` | uuid | 单选成员（第一期不做一日程多成员） |
| `date` | `YYYY-MM-DD` | event=起始日；todo=记录日（仅用于排序，不影响可见性）；countdown=目标日 |
| `time` | `HH:mm` \| null | null = 全天；todo/countdown 恒为 null |
| `endDate` / `endTime` | 同类型 | 跨天 / 精确结束（仅 event 有意义） |
| `allDay` | bool | 由 `time === null` 推导并冗余存储 |
| `repeat` | Repeat \| null | 见 §4；countdown 通常带 `{freq:'yearly'}` 以逐年滚动 |
| `exdates` | string[] | 被"仅此次删除"的日期，升序去重 |
| `overrides` | object | `{ 'YYYY-MM-DD': {title?,time?,endTime?,cancelled?} }` |
| `reminders` | int[] | 提前分钟数，升序去重，≤ 4 项；todo 只允许 `[1440]` 以上的粗粒度 |
| `doneAt` | string \| null | **仅 todo 使用**：null = 未完成、持续显示；非空 = 已完成，从壁挂与日历消失 |
| `pin` | bool | 壁挂屏置顶 |
| `sortOrder` | int | 仅 todo：手动排序，小的在上 |
| `version` | int | 写请求必须带（`If-Match`） |
| `updatedAt` / `updatedBy` | string | 冲突提示用："这条刚被 爸爸 改过" |
| `deletedAt` | string \| null | 墓碑 |

### 3.3 三种形态的行为差异

| | `event` 日程 | `todo` 待办 | `countdown` 倒数日 |
|---|---|---|---|
| 出现在 | 月/周/日日历、今天列表 | **任何日历视图都不出现**；独占壁挂轮播的"待办"页 + 管理"待办"tab | 壁挂右栏倒数日盒（主条目 + 列表） |
| 时间 | 有或全天 | 无 | 无 |
| 完成语义 | 过期即沉底（不打勾） | `doneAt` 打勾后消失，进"最近完成"保留 14 天 | 目标日过后自动滚到下一年（带 yearly）或标记"已过" |
| 提醒 | 任意提前量 | 只支持"当天/提前一天"级 | 提前 1 天 + 当天 |
| 编辑入口 | 点日历格 / 点卡片 | 点待办行的圆圈即完成；文字区进编辑 | 同 event |

**待办的三条硬规矩**（都是为了让它不变成垃圾场）：未完成的一直显示，**不做自动过期、不做逾期变红**；壁挂"待办"页每页 6 条，第 7 条起折叠为"还有 N 条"，完整清单在管理页；只能打勾消失，删除仍是显式操作（避免误触抹掉家人写的东西）。

`Settings`（服务端 `meta` 表键值）：`schemaVersion`、`weekStartsOn`、`alarmHost`（主提醒设备指纹）、`kiosk`（轮播秒数、轮播页序、夜间盘时段）、`theme`（家庭共享的一个值，见 `03` §4.1）、`countdownRotSec`、`membersOrder`。设备级的局部偏好（比如某人手机上只看到自己的日程、某人自己设备上的字号微调）**留在客户端 IndexedDB，不上服务端**——那是视图偏好，不是家庭事实；`theme` 例外，因为壁挂屏的风格属于全家。

## 4. 重复规则 `Repeat`（RRULE-lite）

```json
{ "freq":"daily|weekdays|weekly|monthly|yearly", "interval":1,
  "byWeekdays":[1,3,5], "monthlyMode":"byMonthday|byNthWeekday",
  "nth":2, "until":"2026-12-31", "count":12 }
```

| 字段 | 适用 | 说明 |
|---|---|---|
| `interval` | 全部 | 1–30 |
| `byWeekdays` | weekly | 0=周日…6=周六；缺省 = 起始日星期 |
| `monthlyMode` | monthly | 同日号（短月落月末）或第 N 个星期几 |
| `nth` | monthly+byNthWeekday | 1–5，负数=倒数（-1 = 最后一个周五） |
| `until` / `count` | 全部互斥 | 都空 = 永不终止（展开仍有实例上限护栏） |

**明确不支持**：BYMONTHDAY 列表、复合规则（"最后一个工作日"）、按节假日重复、例外为一整段区间。用户真要，退化成手动建几条，UI 不做承诺。

语义约定（易错，逐条锁死）：

- 每周五重复、起始日是周三 → 首次出现在**下一个周五**（RFC 5545 同款，符合直觉）。
- 每月 31 日、短月 → 落当月最后一天，且该月已出现就不再落。
- `weekdays` = 周一至周五，**不含中国法定节假日调休**（拿不到离线调休表）。UI 必须有这句说明，否则一定被当 bug 报。
- `count` 计数包含被 `exdates` 删掉的实例（与 RFC 一致）。
- 2 月 29 日的年度日程，平年**跳过**（不挪到 2/28）。

### 4.1 编辑重复日程的三选一

| 用户选择 | 实现 |
|---|---|
| 仅此事件 · 改 | `overrides[date]` 写差异字段 |
| 仅此事件 · 删 | `date` 进 `exdates`；若该日已有 override，改写为 `cancelled:true` |
| 此事件及以后 | 原记录 `until = date 前一天`（`count` 折算成 `until`）+ 新建以 `date` 起始的记录 |
| 整个系列 | 直接改；若改起始日需清空 `exdates`/`overrides`（键全部失效），二次确认里写明 |

"此事件及以后"会产生两条记录的变更，服务端必须包在一个事务里（§7.4），否则中途失败会留下"截断但未新建"的半截系列。
单机版没有事务，改为"先写例外、再建独立记录"，两步都成功才算完成；中途失败（掉电、配额满）最坏结果是
"那一天消失了但没挪到目标日"，撤销与重启都会照实显示，不会出现静默丢数据。

### 4.2 拖动改日期 = "仅此事件"的另一种入口（v0.11 新增）

管理页日历里把日程块拖到另一格，语义与"仅此事件 · 改日期"完全一致，实现走 `repo.moveInstance(id, from, to)`：

| 记录形态 | 拖动的落库方式 | 为什么 |
|---|---|---|
| 不重复·单日 | `date = 目标日` | 最直白 |
| 不重复·多日 | `date` 与 `endDate` **按同一位移量平移** | 只改 `date` 会把"三天出差"压成一天 |
| 重复系列 | `from` 进 `exdates` + 在 `to` 新建一条 `repeat:null` 的独立记录 | `overrides` 以实例日期为键，**表达不了"这一次换日子"**，只能拆 |
| 拖回原格 | 直接返回 `null`，不写任何东西 | 不该让一次误拖涨一次 version |
| 待办 / 倒数日 | 抛错（界面上根本不给把手） | 它们永不进日历，没有"日期可挪" |

拖动与滑动删除都返回**可撤销描述**（`{kind:'shift',id,before}` / `{kind:'split',id,from,childId}`），
撤销是原样回写 + 把拆出去那条转墓碑——**墓碑不硬删**，与 §1 的软删总则一致，由 `purgeTombstones(30)` 统一清。

## 5. 展开算法（`domain/expand.js`，与 v0.1 一致）

```
expandRange(events, viewStart, viewEnd):
  for e in events where not e.deletedAt:
    if e.kind != 'event': continue        # ← 硬跳过：待办与倒数日永不进日历视图
    if e.repeat == null:
      if overlaps(e, window): emit instance(e, e.date)
      continue
    for d in candidateDates(e, window):
      if d in e.exdates: continue
      ov = e.overrides[d] or {}
      if ov.cancelled: continue
      emit instance(e, d, merge(ov))
  sort → 📌pin 优先 → 全天 → 开始时间     # 显式比较器，禁止 || 与 ?: 混写（原型踩过）
```

两个独立查询不走展开：`listTodos()` = `kind='todo' AND done_at IS NULL` 按 `sortOrder`→`createdAt`；`listCountdowns()` = `kind='countdown'`，每条算 `daysLeft`（带 yearly 时目标日已过则 +1 年）。

硬性要求：纯函数（只依赖 `Date`）；幂等（同输入两次输出序列化相同）；实例 `id = event.id + '#' + date`；每日程单次展开实例上限 400（护栏），命中则告警不静默丢；查询窗口两端各外扩 400 天以覆盖"上月开始本月仍在持续"的多日/长日程。

必须覆盖的 25 类用例：跨月周、月末溢出（1/31→2/28）、闰年 2/29、"第 3 个周一"跨年、`count` 耗尽、`until` 早于窗口、例外日恰为窗口首日、override 改时间后排序变化、全天与定时混排、周起始日两种、负 `nth`、`exdates` 与 `overrides` 同日冲突、墓碑删除的系列、`cancelled` override、窗口小于日程跨度、`interval>1` 的星期集合漂移、yearly 平年跳过、📌 与全天的排序优先级。

## 7. HTTP 契约

### 7.1 `GET /api/state?since=<revision>（**无变化时只读 meta 一行并返回 `changed:false`**，配额友好是硬要求）`

```json
200 {
  "revision": 1284,
  "schemaVersion": 1,
  "serverTime": "2026-10-06T12:03:11+08:00",
  "members": [ ... ],
  "events":  [ ... ],              // since 为空时全量（含墓碑）；带 since 时仅该 revision 之后变更过的行
  "settings": { ... }
}
```

第一期所有客户端都用全量（家庭数据量 < 1MB），`since` 参数先实现后启用。响应头 `Cache-Control: no-store` ——**绝不允许被 Service Worker 缓存**，否则必然出现"手机上改了、壁挂屏是旧的"这类难查鬼故事。

### 7.2 `PUT /api/events/:id`

请求头 `If-Match: <version>`（新建用 `If-Match: 0`），需写令牌。

```
200 { "event": {...,"version":7}, "revision": 1285 }
409 { "error":"conflict", "current": { ...服务端当前版本... } }
400 { "error":"invalid", "field":"title", "message":"标题不能为空" }
403 { "error":"no_token" }
```

客户端拿到 409 → 展示"这条刚被 {updatedBy} 改过"→ 三选：用我的覆盖（带 `current.version` 重试）/ 放弃我的 / 先看看对方的。

### 7.3 其余端点

| 端点 | 说明 |
|---|---|
| `DELETE /api/events/:id?scope=one\|future\|all` | 软删；`scope` 决定按 §4.1 的哪种语义处理 |
| `PUT /api/members/:id` | 同乐观并发语义；"删除"= `archived=1` |
| `POST /api/auth/pin` | `{pin}` → `{token, expiresIn:43200}`；令牌存 sessionStorage/IndexedDB |
| `GET /api/stream` | SSE：`{type:"changed", ids:[], revision}` / `{type:"heartbeat"}`（25s） |
| `GET /api/export` | 备份 JSON（§8），需令牌 |
| `POST /api/import` | 导入合并，需令牌，**永不隐式删除** |
| `GET /healthz` | `{ok:true, revision, dbSize}` |

### 7.4 服务端不变量

- 写请求在**单个事务**内完成：行更新 + `meta.revision` 自增 + 提交后广播 SSE。
- `updated_at` 由服务端生成，客户端传来的值一律忽略（否则设备时钟漂移会污染冲突判定）。
- 字段长度、枚举、日期格式在**服务端也校验一遍**（客户端校验只是体验，不是边界）。
- SSE 广播失败不影响写结果（fire-and-forget），客户端另有 5 分钟兜底轮询。

## 8. 备份格式

```json

  "revision":1284, "checksum":"sha256:…",
  "members":[ … ], "settings":{ … }, "events":[ … ] }
```

`checksum` 覆盖 `members+settings+events` 的规范化序列化（键字典序、数组按 id 排序）。导入流程：校验 `app`/版本兼容 → 按 `updatedAt` + `version` 合并 → 预览（新增 X、更新 Y、跳过 Z）→ 人工确认 → 事务写入。要真删必须走显式"清空并导入"。

主备份是**服务端数据库文件**（NAS 快照 / `node:sqlite` 的 `backup()` 每日一次留 14 份）；客户端导出降级为"搬家/换设备/给异地亲人"。

## 9. 第一期刻意不做

一条日程挂多成员（用"全家"公共成员覆盖 90% 需求）、分类标签、成员级权限（防改靠 PIN + 引导式访问）、附件与富文本、端到端加密、实时协同编辑（409 足够）、跨设备"谁在线谁提醒"仲裁的自动接管（宁可不响也不三台设备轮流响）。
